## Step 15 & Exercise 3 Security Notes
- **Why `Resource: "*"` with `iam:PassedToService` is dangerous (Step 15):** Even if `iam:PassedToService` restricts the receiving service to `codebuild.amazonaws.com` or `ecs-tasks.amazonaws.com`, setting `Resource: "*"` on `iam:PassRole` allows any principal with pipeline/project creation rights to attach a high-privilege role—such as an account administrator role (`AdministratorAccess`) or a cross-service deployment role—to a build project or task definition and escalate privileges by executing arbitrary commands inside that container.
- **What `aws:SourceArn` closes beyond `aws:SourceAccount` (Exercise 3):** `aws:SourceAccount` only proves that the calling CodeBuild project belongs to account `000000000000`. Adding `aws:SourceArn` pinned to `arn:aws:codebuild:us-east-1:000000000000:project/usms-enrolment-build` prevents another lower-privilege or compromised CodeBuild project in the same AWS account from assuming `usms-codebuild-role`.

## Section 14 — Review Questions

1. **Unchanged deployed application despite green Source and Build stages:** First, if `artifacts.base-directory` is omitted or misconfigured (for example, packing the whole workspace instead of `dist`), `BuildOutput` contains `dist/imagedefinitions.json` nested inside a `dist/` subdirectory rather than at the artifact root, causing the deploy stage to miss the updated file or fall back to an old definition; inspecting `unzip -l outputs/lab-11-buildoutput.zip` distinguishes this by showing `dist/` prefixes on archive entries. Second, if the source zip was packed from the parent directory (`app/buildspec.yml` instead of `buildspec.yml` at the root) or pointed at the wrong S3 key while an older artifact persisted, the build either read stale files or used a fallback spec; running `unzip -l outputs/usms-enrolment-src.zip` distinguishes this by revealing a top-level `app/` directory prefix.

2. **Why CodePipeline requires S3 versioning:** CodePipeline executions are asynchronous and multi-stage; each execution must pin an immutable `VersionId` for the exact source archive it fetched at start time so that later stages (and audit logs) reference that exact snapshot even if a developer uploads a newer zip to the same S3 key seconds later while the pipeline is still running.

3. **Why `iam:PassRole` is not redundant:** Creating a CodeBuild project (`codebuild:CreateProject`) is a control-plane configuration action, whereas assigning a service role to that project delegates all permissions attached to that role to whoever can trigger builds or modify `buildspec.yml`. Separating `iam:PassRole` lets administrators grant developers permission to create and configure build projects while restricting which IAM roles those projects are allowed to assume, preventing privilege escalation via an administrator role.

4. **Two-role design (`usms-codebuild-role` vs. `usms-codepipeline-role`) — for and against:** Separating the roles enforces least privilege and limits blast radius: untrusted code and third-party dependencies execute inside CodeBuild under `usms-codebuild-role` (which has no `iam:PassRole`, no `codepipeline:*`, and no ECS deploy rights in Lab 12), while `usms-codepipeline-role` orchestrates stage transitions without executing build scripts. The strongest argument against splitting them is operational overhead: two roles and two policies double the IAM boilerplate, require explicit `iam:PassRole` handoffs between them, and create more places where a subtle ARN or policy version mismatch can break deployments.

5. **Three heredoc forms (`<< 'BUILDSPEC'`, `<< META`, and `<< EOF`):** In Step 8, single-quoted `<< 'BUILDSPEC'` prevents the outer shell from expanding `$USMS_RELEASE`, `$ARTIFACT_DIR`, and `${CODEBUILD_BUILD_ID:-local}` when writing `buildspec.yml`; if unquoted `<< BUILDSPEC` were used, the outer shell would expand them to empty strings or `"local"` at file-creation time, silently hardcoding blank/local values into `buildspec.yml` with no syntax error. Inside `buildspec.yml`, unquoted `<< META` is required so the build container's shell expands `$SERVICE_NAME` and `$USMS_RELEASE` when generating `build-metadata.json`; quoting it as `<< 'META'` would write literal `$USMS_RELEASE` strings into valid JSON without raising any error. In Step 21, unquoted `<< EOF` expands `$(aws ...)` command substitutions at write time so `configs/lab-11.env` stores static values; quoting it as `<< 'EOF'` would write raw `$(aws ...)` commands into `configs/lab-11.env`, which still parses as valid shell syntax when sourced later (re-querying AWS dynamically instead of recording a point-in-time snapshot).

6. **Removing `pre_build` configuration validation:** A colleague is right only when the build stage produces no expensive artifacts, runs in seconds, and deploys immediately to an isolated environment where deployment validation is instantaneous and zero-cost. They are expensively wrong when building container images, running long test suites, or deploying across shared/production stages: catching a wrong container name or port in `pre_build` fails in seconds before building/pushing images or triggering slow ECS/ALB health-check rollouts and rollbacks.

7. **Audit evidence chain for release `r4` and its weakest link:** The evidence chain starts with the git commit history for `labs/lab-11-cicd/app/VERSION` (`r4`), links to the S3 object version history on `s3://usms-pipeline-artifacts/source/usms-enrolment-src.zip` (`VersionId` and `LastModified` timestamp), continues through the CodePipeline execution record (`get-pipeline-execution` linking that source `VersionId` to a specific `CODEBUILD_BUILD_ID`), and terminates in `build-metadata.json` inside `BuildOutput` recording `"release": "r4"`, `"builtAt"`, `"buildId"`, and `"sourceVersion"`. The weakest link in this lab's setup is the manual packaging and `aws s3api put-object` step (`usms-pack-source.sh`), because S3 has no cryptographic attestation proving that the uploaded zip was built cleanly from an unmodified git commit rather than a locally edited working tree.
